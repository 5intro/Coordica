## 第四轮：已确认

| 编号 | 用户决定 | 对基线的影响 |
|---|---|---|
| R14 | 后续自动批准不仅覆盖普通任务执行，还能按预设政策批准普通范围扩展。长期目标是自动化项目开发，人主要介入重大决策和报错。 | 扩展 R13。普通扩展需形成新的授权版本并遵守已有门禁；重大决策和需升级的报错分类待确定。R10 受保护变更人工批准尚未被撤销。 |
| R15 | 使用 GitHub 公开仓库；除用户自身授权身份外，其他人不能直接上传或合并。 | 收敛 U10 的托管位置与公开性。公开访问不授予写入权限；中心代表用户执行已授权上传与自动集成。外部贡献不会自动转化为已授权任务。具体平台配置尚未执行。 |
| R16 | 中心和 Runner 使用 Go；Web 使用 React + TypeScript；首期数据库使用 SQLite。 | 收敛 U08 的栈与数据库。优先跨电脑部署简单、后台依赖少、执行可控和未来自动化；不以后台单语言覆盖全部产品为目标。 |
| R17 | 中心是模块化单体，React 构建产物由中心提供。 | 首期不引入微服务、Redis、独立消息队列或通用 Agent 编排框架。 |
| R18 | API-first；Web 为主要人工入口，同时保留精简 CLI 和 MCP。 | 所有入口复用中心授权、状态机和审计；运行不依赖浏览器持续打开。 |
| R19 | Agent 优先使用官方程序化接口和结构化事件，不解析交互式终端显示文本。 | 适配器显式报告取消、恢复、审批等能力；不同工具能力不假定一致。 |
| R20 | 协议使用版本化、语言无关契约，尽量生成前后端类型并做运行时输入校验。 | 任务状态和恢复逻辑不绑定特定 Agent SDK。 |
| R21 | 首期不预先引入多套后台运行环境；未来确有需要时可增加 TypeScript 或 Python 适配组件。 | Go 首期直接管理官方程序接口和 CLI 子进程；具体外部工具自身运行时仍由工具决定。 |
| R22 | 验收覆盖实际部署、子进程终止、断线恢复、重复消息、旧租约拒绝、主线变化与预算耗尽。 | 页面功能可用不足以证明首版完成；需在真实执行与故障场景验证。 |

用户补充的产品方向：

> 因为我的目标是做一套自动化的项目开发系统，不能什么都要人介入批准，除了重大决策和报错。因为还有测试在兜底

长期方向与首版阶段 A 分开：阶段 A 先实现手工任务的受控执行与自动集成；后续在项目授权范围内自动规划与推进，不能将自动批准误解为删除门禁。

## 原基线缺口与 v0.2 处理

这些是审阅发现，已在草案中具体化，不声称是用户已逐项批准的决定。

1. 原基线 9.2/9.4 的执行归属歧义：v0.2 第 10.3 节将候选受理定义为授权交接点。
2. 旧 Run 与私人 Git 写权限：第 4/6/10 节区分平台凭据和私人权限，并隔离 Run 目录与交接引用。
3. 范围比较对象：第 7 节分别检查 B→H 与 M→C，覆盖贡献与实际合并修复。
4. Git 与 DB 的权威来源：第 11/13 节以中心已激活政策为执行权威，仓库政策不自动生效。
5. 恢复边界：第 6/13/14 节只承诺已持久化检查点，补齐一致备份材料清单与恢复对账。
6. 交叉审阅补充：第 6/10/12/14 节补齐扩围资源等待循环、候选替代、暂停生效点、次数上限最后一次成功结果和备份引用闭包。

## 核验事实（不等于产品决定）

- 当前 Coordica 工作目录在本轮开始时为空，尚无可运行的协调器；自举必须有初始人工辅助构建阶段。
- 本机 PATH 可用 Codex CLI 和 Claude Code。没有检测到 dsh；这不证明它在另一台电脑不可用。
- 官方 DeepSeek Harness 使用 dsh 命令；其 ACP 接口支持会话创建、恢复、取消、关闭和语义事件。此处依据官方当前文档，尚未在本机安装版本上实测。
  - [CLI 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md)
  - [ACP 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/acp/acp/README.md)
- GitHub 个人仓库的 owner 与受邀 collaborator 有不同权限；公开可见不自动授予直接推送或合并权限。公开仓库可用分支保护。
  - [个人仓库权限](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)
  - [分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- 设计将平台远端上传与主线更新收敛至中心，开发端提交固定代码材料。不给模型进程注入写凭据不等于屏蔽私人设备已有的凭据；不声称私人环境中任意命令都无法以用户身份推送。

## R32：统一 MCP 初始化入口（2026-10-11）

用户确认第二台电脑为 Windows，已安装并登录 dsh。用户要求 macOS、Windows、Linux 使用同一流程：安装 MCP 并下达初始化指令，由 MCP 探测本机信息并交给 Runner，再连接中心。

实现据此增加启动前的本地 MCP，与已有绑定 Run 的受限业务 MCP 分开。初始化采集 OS、架构、Git/工具路径与版本，接收用户提供的中心地址、一次性配对码和必要的公共 CA 信息；由 Runner 完成配对，再通过用户级服务独立运行。MCP 不读取模型认证文件、不替 owner 批准任务、不持有发布凭据。`inspect_environment` 与 profile 导出保留为诊断方式，手动执行 pair/runner 不作为主要接入流程。

本地版本探测不能证明认证有效，后台服务启动请求成功不能证明已完成双机开发验收；真实 Windows dsh 联调待安装后的实际连接验证。
