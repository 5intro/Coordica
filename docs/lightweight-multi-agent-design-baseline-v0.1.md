**整理日期：** 2026-10-10  
**适用对象：** 面向 10 个及以下 Agent 的个人开发者与小团队。Agent 数量、同时运行的任务数量、人类成员数和设备数分别统计，不相互等同。  
**来源：** 本轮对话中的构想，以及随后已获认可的修正建议。本文不对第三方工具的当前能力作新的验证或保证。

> 建立一个轻量的任务与代码集成协调器：Agent 负责理解、规划、实现和解决问题；程序负责状态、权限、版本、验证和放行。系统能够推进已授权工作，但不能自行扩大目标、绕过门禁或无限重试。

本文将已经确定的架构原则和行为约束写为设计要求。数据库产品、执行隔离技术、具体状态枚举、接口字段、超时和预算数值等尚未定稿的事项集中列在文末；推荐候选不等于已经选定。

## 1. 目标、边界与核心决定

### 1.1 要解决的问题

同一个项目由多个开发 Agent 在不同工作目录或设备上执行时，系统应能回答：当前要实现什么、谁获准执行、允许改哪里、依据哪个版本、如何验证、由谁放行，以及失败后如何接续。

核心目标是降低重复劳动、越界修改、集成失败、上下文丢失和失控运行，而不是追求 Agent 数量或让所有节点始终忙碌。

“轻量”指减少部署单元、常驻模型会话和重复建设，不指删除事务、身份认证、审计或质量门禁。

### 1.2 已确定的核心决定

| 编号 | 设计决定 |
|---|---|
| D01 | 保留人提出需求的需求池，以及承载已拆解工作的任务池；需求与任务可多对多关联。 |
| D02 | 使用单中心协调架构；成员执行端主动接入中心，不建立 Agent 间的直接网络通信体系。 |
| D03 | Requirement、Leader、实现、冲突分析、测试分析是逻辑职责，不要求各有常驻进程或永久会话。 |
| D04 | 普通调度、状态流转、权限校验、真实合并、测试执行和发布控制由程序完成。 |
| D05 | 按独立功能组织交付；共享接口、迁移、基础设施等可以作为前置或专门任务。 |
| D06 | 范围授权绑定任务及有效执行尝试，不将目录永久分配给某个 Agent。 |
| D07 | 以任务为单位使用短生命周期分支和隔离工作目录；不使用一个 Agent 一条永久开发分支的模式。 |
| D08 | 并行开发，串行集成；每个受保护目标分支只有一个受控的集成入口。 |
| D09 | 集成依据实际 Git 变更和合并候选的验证，不依据 Agent 自报的文件清单或测试总结直接放行。 |
| D10 | 项目完整上下文存储在仓库与数据库中；Leader 的会话不是权威记录。 |
| D11 | 本地执行端由 Runner、MCP 接口和编程工具适配器组成；MCP 不承担全部执行管理职责。 |
| D12 | 测试结论、发布批准和实际部署分离；生产操作由受控发布执行器实施。 |
| D13 | 数据库既记录审计，也保存任务归属、授权、候选版本和恢复所需状态。 |
| D14 | 自主推进受授权、依赖、预算、重试上限和暂停机制约束。 |
| D15 | 原始需求、决策和交付证据可追溯；系统可备份、恢复、导出，并能更换 Agent 会话接续。 |

### 1.3 首期设计边界

首期方案以单项目、单 Git 仓库、单受保护主分支作为设计和测试基线。这是当前工作假设，尚未冻结为永久产品限制；是否首期支持多仓库或多项目并行，见待决事项 U01。

暂不建设多主中心、自动主节点选举、Agent 全互联网络、自研 NAT 穿透、完整工作流编排语言、插件市场或通用多 Agent 框架。也不追求自动避免所有语义冲突。

中心不可用时，系统允许暂时失去协调能力，不能把高可用要求偷偷转化为分布式系统建设。恢复后的状态对账是必需能力。

## 2. 最小架构与职责划分

### 2.1 两类部署单元

```text
人类成员
   │ 提需求、确认范围、处理决策、验收
   ▼
中心协调器
   ├─ API 与轻量操作界面
   ├─ 需求池、任务池、状态机
   ├─ 身份、任务领取、范围授权、资源占用
   ├─ 事件处理、依赖调度、预算与暂停
   ├─ 集成队列、验证与发布控制
   └─ 本地事务数据库、审计及产物索引
   ▲
   │ 执行端主动建立的受认证连接
   ├───────────────┬────────────────┐
   ▼               ▼                ▼
成员执行端 A     成员执行端 B     受控验证／发布执行端
   ├─ Runner       ├─ Runner        └─ 同一执行端类型，能力与凭据不同
   ├─ 本地 MCP     ├─ 本地 MCP
   ├─ 工具适配器   ├─ 工具适配器
   └─ 任务环境     └─ 任务环境
      Codex 等        Claude Code 等

代码交换：Git 远端仓库
验证与产物：受控执行环境；可复用已有 CI 和产物存储
```

验证或发布执行端可以使用同一种 Runner 部署形式，不因此增加一套独立平台。是否必须使用专门设备、如何做进程与凭据隔离，取决于最终的信任边界。

轻量界面至少应能查看需求、任务、当前运行、授权申请、阻塞、集成候选、验证证据和关键决策。第一版不要求复杂的组织管理或可视化流程编辑器。

### 2.2 人、模型与程序的职责

| 主体 | 负责 | 不负责或无权自行决定 |
|---|---|---|
| 人类责任人 | 产品目标、范围与预算授权、重大取舍、必要的风险批准和交付验收 | 不必逐条指挥实现细节 |
| Requirement 角色 | 归一化需求、识别重复和歧义、提出拆分合并、形成验收建议 | 不自行改变产品方向或把分析完成视为已获授权 |
| Leader 角色 | 提出执行计划、处理复杂依赖、协调范围调整、形成决策请求 | 不替代数据库、身份校验、任务锁和发布门禁 |
| 实现角色 | 在授权范围内开发、自测、报告阻塞并提交固定版本变更 | 不直接修改主分支，不自行扩大范围或宣布独立验证已通过 |
| 冲突分析／评审角色 | 分析语义冲突和风险，提出一个可执行的修复方案 | 不用自然语言意见替代实际合并、测试和批准 |
| Test 角色 | 设计补充测试、探索性验证、分析失败与发布风险 | 不跳过最低门禁，不自由持有或使用生产管理权限 |
| 中心与受控执行器 | 状态、授权、执行、证据、集成、放行、对账 | 不根据模型一句“完成”直接改变权威事实 |

角色配置是执行策略，不是安全边界。真正的安全边界来自身份、服务端授权、执行环境和凭据控制。把同一个高权限进程换成不同角色提示词，不能实现权限隔离。

### 2.3 按事件调用模型

普通依赖检查、心跳处理、超时、队列推进、Git 检查和固定测试由程序处理。需求需要解释、任务存在复杂取舍、范围申请有设计影响、测试失败需要分析时，才调用相应角色。

Leader 不要求始终运行。任务、范围申请和决策记录可以让新的 Leader 会话恢复工作。

## 3. 需求池、任务池与变更流转

### 3.1 需求记录与确认

原始需求保留提出者、原文、时间和后续版本。Requirement 角色的整理结果作为分析或新版本保存，不能覆盖掉原始诉求。

一个需求可以拆成多个任务；多个需求也可以共同约束一个任务。关系中需要能区分实现、验证和修复等用途，具体字段尚未冻结。

分析过程包括目标用户与场景、成功条件、非目标、歧义、依赖和最危险的假设。对于尚未验证的价值或技术假设，可以提出有预算上限的调研、原型或验证任务，而不是立即进入全面实现。

模型建议与执行授权分开。影响产品目标、范围、成本或用户行为的决定，需要人确认，或落在已有的明确授权范围内。可批准一个迭代或目标范围，避免对每个小任务重复审批；具体授权粒度待定。

### 3.2 任务进入可执行队列的条件

任务已有清晰目标、关联依据、验收方法、依赖、范围、责任归属和预算边界，并且获得执行授权，才可以进入可执行状态。

范围和验收仍不明确的任务留在分析或待决阶段。开发中冒出的新想法不能因为“顺手能做”直接加入当前任务。

### 3.3 需求版本变化

已确认需求发生变化时，保存新版本，标出受影响的任务、在途执行和既有验收证据。系统不能静默改写旧约定，然后把所有未完成任务视为已经自动接受新要求。

受影响任务需要重新确认继续、暂停、取消或调整。是否需要重新测试，依据修改后的验收和实际影响判断；审批规则仍受授权政策约束。

### 3.4 工程问题的分流

| 事件 | 去向 |
|---|---|
| 未完成任务的实现或自测失败 | 原任务的修复尝试 |
| 已交付功能出现缺陷 | 缺陷任务，关联原需求、版本和复现证据 |
| 单纯合并适配或机械冲突 | 原任务返工或关联集成修复任务 |
| 接口或架构冲突 | Leader 协调并形成决策，随后生成明确修复任务 |
| 产品行为、范围或验收改变 | 需求池与相应确认流程 |
| 运维、安全、依赖或技术债问题 | 对应维护任务；涉及范围取舍时再申请决策 |

任务池不仅接收新功能任务，也接收已授权的缺陷、验证、集成修复和维护任务。Requirement 角色不是所有工程问题的必经审批人。

## 4. 任务契约与生命周期

### 4.1 任务契约的必要语义

下表定义最低信息要求，不冻结数据库列名或 API 字段名。

| 类别 | 必须表达的信息 |
|---|---|
| 身份与依据 | 项目、任务、关联需求及版本、人类责任人 |
| 交付边界 | 目标、范围、非目标、任务类型 |
| 验收 | 可观察的通过条件、失败条件、必要检查与交付证据 |
| 依赖 | 前置任务、接口契约、共享资源及已解决的决策 |
| 执行基线 | 固定的代码基线与上下文／规范版本 |
| 权限 | 可读范围、源代码可改范围、受保护路径、允许的外部动作 |
| 限制 | 执行预算、重试边界、停止条件 |
| 交接与恢复 | 分支、当前提交、验证结果、阻塞、下一步及必要恢复说明 |

同一任务的契约可版本化变更，但在途执行不能通过读取到新文字就自动获得更大权限。扩大范围或改变验收必须形成明确的新授权和影响处理。

### 4.2 任务、运行与发布分开记录

**任务**代表要完成的工作。**Run** 代表一次实际执行尝试。**发布**代表把一组指定变更对应的产物交付到某个环境。

任务可能经过多次 Run；多个任务可以进入同一次发布；同一提交可以有多次不同环境的验证。这些关系不能压成一个“完成”字段。

任务生命周期至少区分以下语义节点，具体枚举待定：

```text
草拟／待确认 → 可执行 → 执行中 → 待集成 → 已集成
                                              │
                                              ▼
                                   已发布／已交付 → 已验收

旁路：阻塞、待人决策、取消；执行失败记录在对应 Run 中并明确后续处理。
```

不需要发布的调研、文档等任务，可以依据任务类型跳过不适用阶段，但必须有对应验收证据，不能由执行者临时决定跳过。

### 4.3 不能混淆的完成含义

运行正常退出不等于任务完成；自测通过不等于集成通过；已集成不等于已发布；已发布不等于用户验收通过；所有关联任务结束也不自动证明某项需求已经满足。

关键状态由真实证据和授权决定，不开放为“Agent 可任意修改的状态文字”。

### 4.4 执行结果与交接

每次执行结束至少记录：固定提交、实际修改、自测命令与结果、未执行的检查及原因、剩余风险、下一步。

在不同节点之间接手时，可交接代码必须已进入授权的远端分支或可取得的补丁／产物。不能只留下“代码在原电脑上”的描述。

重启、换会话或换执行者时，先核对仓库与服务端实际状态，再决定复用或重建环境。聊天摘要不能代替这一步。

## 5. 调度、身份、执行归属与恢复

### 5.1 分开识别人、节点、Agent、任务和 Run

| 实体 | 含义 |
|---|---|
| 人类成员 | 授权、责任与协作主体 |
| 节点 | 实际运行 Runner 的设备或受控执行环境 |
| Agent | 具有角色、工具类型和能力配置的逻辑执行者 |
| 任务 | 一项可独立追踪与验收的工作 |
| Run | 一次执行尝试，绑定实际 Agent、节点和授权 |

一个节点可承载多个 Agent，一个 Agent 可先后执行多个任务，一个任务可以经过多次 Run。网络地址不充当稳定身份，Agent ID 也不等于身份认证凭据。

### 5.2 调度方式

Leader 提出任务分派或计划，中心程序检查授权、依赖、范围占用、节点能力、容量和预算，然后才能领取并执行。

任务领取必须原子化。一个普通实现任务在同一时刻只有一个有效执行归属；确需并行的工作应拆成独立子任务，评审和验证则作为单独活动记录。

独立功能可以并行；共享接口、迁移、公共配置等通过前置任务、依赖和资源占用控制顺序。没有就绪任务时正常停止，不自动创造新需求维持运行。

### 5.3 执行租约与分配代次

有效执行归属带有租约和单调推进的分配代次。重试、换节点或换执行者时，中心需要明确旧归属是否失效，并防止旧执行重新获得写入当前状态的权限。

例如：Run A 失联后任务转给 Run B，A 恢复时提交的结果可保存为历史或参考，但不能覆盖 B 的状态、扩大授权或触发主线合并。

租约失效意味着中心不再承认该执行的后续授权，不意味着远端进程已经被物理终止。接管前需要核实可能仍在运行的旧执行，并隔离其外部副作用。

### 5.4 任务占用与运行租约不是一回事

运行租约回答“谁现在有权执行”；集成占用回答“哪些尚未集成的变更仍会影响后续任务”。

任务自测通过、进入集成队列后，Run 可以结束，但相关热点资源不能自动被当作完全空闲。释放、移交和保留占用必须由任务及集成状态决定。具体策略见 U06。

### 5.5 离线与恢复

心跳用于判断节点与进程是否可联系。失联后是否允许继续纯本地开发、多久重新分派，尚未确定；无论采用哪种策略，过期执行都不能直接合并主线或发布生产环境。

恢复时检查中心记录、代码提交、工作目录、已有外部动作和未完成验证。复用会话只是优化，不是恢复正确性的前提。

<a id="s06"></a>
## 6. 任务范围、共享资源与冲突预防

### 6.1 冲突控制分三层

| 层面 | 风险 | 对应机制 |
|---|---|---|
| 文件与目录 | 重叠修改、公共配置争用、越界写入 | 任务范围、受保护路径、热点资源占用、真实差异检查 |
| 接口与行为 | 文件不重叠但接口、权限或业务语义不兼容 | 接口契约、依赖、版本化决策、集成与行为测试 |
| 运行环境 | 共享数据库、端口、迁移序列或测试账号冲突 | 独立环境／命名空间，或受控互斥占用 |

不存在“按功能拆分后就无须处理冲突”的假设。目录控制是一层防线，不是完整正确性证明。

### 6.2 源代码范围与运行时写入范围分开

任务可以被限制只修改某些源代码，但构建和测试仍可能需要写临时目录、缓存和生成产物。这两类写入分别管理，避免把每次正常测试都变成范围申请。

受保护路径包括能够改变验收或权限的文件类别，例如 CI、测试入口、发布策略和关键公共配置。具体路径清单由项目定义，不能由实现者临时降低。

### 6.3 范围申请流程

```text
发现超出当前授权的必要修改
  → 在越界修改前提交申请
  → 附理由、路径／资源、受影响契约、备选方案和风险
  → Leader 分析是否合理、是否影响其他任务
  → 中心原子校验占用与审批条件
  → 批准、排队、拒绝，或升级为人类决策
  → 若批准，生成有版本的授权并通知相关执行
```

已获得范围批准，不代表自动获得其他外部权限。例如获准修改部署脚本，不等于获准执行生产部署。

### 6.4 三重落实

**执行前：**中心校验范围、资源占用与授权。

**执行中：**Runner 配合隔离机制限制源代码和外部资源访问；不能强制限制的环境必须标记能力降级。

**提交时：**可信集成入口从 Git 对象和实际候选计算变更，检查新增、删除、重命名及受保护路径等情况，不信任自报清单。

“阻止越界变更进入主线”与“阻止本机发生越界写入”是不同保证。后者依赖实际操作系统和执行隔离，不能仅凭 MCP 或规范文件声明已经实现。

范围绑定任务及执行授权，不作为 Agent 的永久领地。热点路径优先采用排他控制；普通区域不默认全仓库加锁。锁粒度、等待、释放及死锁处理仍待细化。

<a id="s07"></a>
## 7. 持久上下文与项目规范

### 7.1 三类上下文和权威来源

| 类型 | 内容 | 权威来源 |
|---|---|---|
| 稳定项目知识 | 产品目标、架构、接口契约、模块边界、规范、验收依据、重要决策、操作手册 | Git 仓库内版本化文档 |
| 动态执行事实 | 需求与任务版本、负责人、运行、授权、占用、阻塞、候选、证据与批准 | 中心数据库及关联事实来源 |
| 本次执行上下文 | 当前任务需要的文档片段、固定基线、当前授权、依赖、未解决问题 | 启动时从前两类来源组装的有版本上下文包 |

Git 和实际运行环境分别提供代码、发布状态等事实，中心保存引用与经过核对的状态。不要维护互相独立、依靠手工同步的多套任务看板。

### 7.2 Leader 的上下文责任

Leader 维护知识索引、架构相关摘要和必要的决策，不将个人会话当作项目唯一记忆。摘要必须能追溯到文档、任务或真实事件；发现摘要与权威记录冲突时，需要报告并修正。

“整体已经完成的情况”按计划、实现、自测、集成、发布、验收分别汇总。模型不能仅根据成员描述把计划工作标为已交付。

新任务按需获取相关上下文，不默认装入全部日志和所有历史。影响中的规范、接口或需求变更，应触发在途任务的影响检查。

### 7.3 规范文件初始化

项目规范保持一个权威来源。执行端初始化时，根据开发工具适配器将其接入对应的指令加载机制；具体文件识别与重载行为需要在选定工具版本上验证。

写入应保留既有用户内容，采用受控管理区块或引用，并记录版本；不能每次连接都覆盖整份文件。规范中不写个人凭据、机器令牌和动态任务状态。

共同规范放仓库；任务级动态信息通过启动上下文或 MCP 提供。规范更新后，显式判断当前 Run 是否需要重启、重新确认或重新验证，不能假定文件修改必然被运行中的会话读取。

### 7.4 可接续性要求

移除任何一个模型会话后，新会话都应能依据仓库、数据库、代码引用和检查点继续工作。恢复过程中允许调用模型重新理解，但不允许靠猜测补全缺失的授权或执行事实。

<a id="s08"></a>
## 8. Runner、MCP、注册与通信

### 8.1 一个执行端软件包，三类内部职责

| 组成 | 职责 |
|---|---|
| Runner | 注册、接任务、领取与续约、准备环境、启动停止受管进程、收集证据、恢复与清理 |
| 本地 MCP 接口 | 向 Agent 提供查询任务、读取上下文、申请范围、报告阻塞、提交结果等受限工具 |
| 工具适配器 | 适配 Codex、Claude Code 等工具的调用、权限、输出、退出、取消与会话行为 |

MCP 是模型可使用的工具入口；是否可以调用某个动作，仍由中心与 Runner 校验。模型传入的身份、授权和测试结论不能直接当作可信事实。

第一版可以先实现一个开发工具的完整适配器，再扩展其他工具；优先顺序尚未决定。

### 8.2 两种执行模式

**交互模式：**人类启动自己的开发会话，通过 MCP 查询或领取工作。中心不能因为接入了 MCP 就任意控制这条私人会话。

**托管模式：**成员明确批准 Runner 在限定资源和权限内接收任务，由 Runner 启动、跟踪、取消受管执行。

两种模式共享任务与证据模型，但控制能力不同。是否两者都进入第一版，见 U03。

### 8.3 注册和身份认证

节点首次注册通过邀请、管理员批准或等效的明确授权流程。中心分配稳定身份，并发放可撤销、限制项目与能力的凭据；不允许匿名请求自行获得团队执行权。

中心根据认证上下文判断调用者身份，并核对报文中的关联 ID。仅知道 `agent_id`、IP 或端口不能执行任务操作。

节点可以报告工具类型、版本、隔离能力和运行容量；关键能力需要在接入检查或运行验证中确认，不能把自报能力自动视为强保证。

具体令牌体系、密钥存储、轮换和审批流程待定。

### 8.4 星型网络与部署方式

所有执行端主动连接中心，协作消息经中心路由和审计；不要求每台成员电脑开放入站端口。成员之间不维护直接的 MCP 会话或共享工作目录同步协议。

| 场景 | 设计方向 |
|---|---|
| 中心和执行端同机 | 使用回环连接或本地 IPC；本地模型工具按标准 MCP 接入 |
| 同一局域网 | 执行端连接指定中心，保留身份认证 |
| 跨网络且有服务器 | 执行端连接中心的受认证、加密接口 |
| 跨网络但无自有公网服务器 | 复用既有加密组网或受控转发服务，让成员能访问某台中心设备 |

“无自有公网服务器”不等于“无中心、无网络可达性条件或不需要任何第三方连通服务”。中心电脑关机时，暂停中心协调；第一版不自研穿透、中继和自动换主。

具体组网产品不在本设计基线中选定。

### 8.5 业务协议

复用成熟传输与标准 MCP，不为任务协调自研底层网络协议。Runner 与中心使用 HTTPS API 加长轮询是当前优先候选，最终传输与协议版本见 U09。

业务消息需要表达以下语义：协议版本与消息类型、消息 ID 与幂等键、项目／任务／Run 关联、节点和 Agent 关联、预期任务版本、分配代次、因果关联与正文。

IP 和端口用于寻址或诊断，不作为业务身份或每条消息的必填权威信息。Agent 类型编码的具体形式尚未冻结。

协议须允许重试、去重、过期请求拒绝、明确错误、取消和对账。可以重复投递消息，但不能因此重复执行不可重复的业务动作。

<a id="s09"></a>
## 9. Git 隔离、集成队列与冲突处理

### 9.1 任务级分支和工作目录

一个可独立交付的实现任务对应短生命周期分支和隔离工作目录。可以使用 Git worktree，但 worktree 不作为权限沙箱。

重试时可在核验状态后复用原任务分支或工作目录，但不允许新旧有效执行同时写同一个工作目录。换人或换节点时使用明确的代码交接。

代码经共同 Git 远端或受控补丁／产物交换。成员工作目录不是共享事实来源。成员凭据不应允许绕过受控集成入口直接写受保护主分支。

### 9.2 提交固定候选

成员提交集成申请时，绑定固定代码提交、开发基线、任务及授权版本和自测证据。自报文件列表可用于说明，但中心必须独立计算实际变更。

提交后分支新增代码不自动进入旧候选。新的提交形成新候选，旧候选对应的检查不能直接移植为新版本的通过证明。

候选被中心受理后，由集成控制器以自身授权推进，不要求提交者持续保持会话在线。能否继续集成取决于任务、授权与候选是否仍然有效，而不只取决于开发端是否在线；在候选受理前已经失效的执行不能借此提交新候选。

### 9.3 B、H、M、C 四个版本

| 标记 | 含义 |
|---|---|
| B | 本次开发／交接采用的基线提交 |
| H | 成员申请集成的固定提交 |
| M | 处理候选时受保护主分支的实际提交 |
| C | 将 H 集成到 M 后准备验证并落地主线的候选提交 |

成员自测绑定实际被测试的 H，以及所用环境和配置；B 是可追溯的开发依据，不是“主线当前状态”的替代。

集成门禁验证 C。提交关系、共同祖先和真实 Git 合并结果决定候选，不通过提交时间、SHA 大小或文件名重叠猜测能否合并。

### 9.4 串行集成流程

```text
取得一个待集成候选
  → 核验任务、执行归属、授权与固定提交
  → 读取目标主线 M
  → 计算实际变更并执行真实试合并
  → 检查任务范围、受保护路径和必要审批
  → 生成候选 C
  → 在受控环境执行必需验证和评审
  → 复核授权、候选与主线仍然有效
  → 仅在目标仍为 M 时将主线更新到已验证的 C
  → 保存结果并核对外部实际状态
```

验证期间主线变化、候选变化或关键授权失效时，不能使用旧结果放行。重新构造并验证候选，或明确取消本次候选。

最终落地主线的版本必须与验证对象严格对应。合并、变基或压缩合并策略不能在验证后悄悄改变待交付结果；具体 Git 托管和条件更新实现尚待选定。

文件不重叠不构成免测条件。同一文件被多人修改也不一定需要模型协商；先使用实际合并结果判断机械冲突，再通过测试和评审处理语义风险。

### 9.5 冲突处理

| 类型 | 处理方式 |
|---|---|
| 可自动干净合并 | 不启动多方讨论，继续候选验证 |
| 机械性冲突 | 记录准确冲突及版本，由唯一修复者处理 |
| 接口／架构冲突 | Leader 汇集契约与差异，记录决策，指定唯一落地者 |
| 产品行为或范围冲突 | 返回需求确认；必要时请求人类裁决 |

最后提交的任务负责适配已接受主线可以作为候选默认策略，但不代表先合并的实现一定正确。最终责任选择规则尚待确定。

冲突修复关联原任务、相关候选、决策与新提交。纯技术修复不必绕经 Requirement 角色；修改产品约定才需要回到需求池。

协商与修复受预算和轮数约束。达成口头共识后仍要重新执行相应验证。

<a id="s10"></a>
## 10. 测试、发布与交付验收

### 10.1 测试分层

| 层次 | 目的 | 验证对象 |
|---|---|---|
| 成员自测 | 及早发现实现问题 | 固定的成员提交与任务验收条件 |
| 候选集成验证 | 决定变更能否进入主线 | 实际合并候选 C |
| 发布验证 | 判断某个指定产物能否部署到目标环境 | 版本、构建产物、配置、迁移和必要环境检查 |
| 发布后验证 | 判断实际交付是否健康、关键路径是否可用 | 指定部署及其真实环境 |

测试组合由固定最低门禁、按变更范围选择的检查，以及 Test 角色提出的补充验证构成。Leader 可以建议扩大测试或申请政策允许的例外，不能仅凭判断降低固定门禁。

最低测试集合、何时执行全量、允许哪些例外，属于待决事项 U07。影响不清楚时不能以“可能没关系”作为直接放行依据。

### 10.2 测试证据

测试证据包括实际代码／产物版本、测试配置与环境、执行命令、执行结果和日志或产物引用。未运行的测试明确标记未验证。

成员自测用于反馈和候选材料，不单独授权主线合并。决定放行的检查由可信执行链实施；模型摘要不能替代执行事实。

签名或节点身份只能说明报告来源，不自动证明报告正确。如何建立可信验证环境属于部署与信任模型的待决事项。

验收标准、测试入口、CI 和发布规则的变更须显式标记并审查，不能让实现者通过删除测试或放宽规则获得通过。

### 10.3 受控发布

```text
固定版本／产物的验证与风险报告
  → Leader 提出发布请求
  → 校验发布策略与必要批准
  → 受控发布执行器部署指定产物
  → 运行健康检查与发布后验证
  → 记录成功，或按事前批准的方案恢复／止损
```

发布执行器是受控程序，不要求增加一个常驻 Release Agent。Test 角色负责证据和建议，不获得自由 SSH、任意运行生产命令等开放式权限。

批准绑定具体环境、版本／产物和允许动作。批准后主分支变化，不等于新版本也已获准上线；不得把浮动的 `latest` 直接当作批准对象。

开发或测试代码的运行环境与高权限合并、部署凭据分离。某个角色能够分析发布失败，不意味着它可以获取所有生产凭据。

哪些操作自动批准、哪些需要人确认、是否分环境实施，尚未定稿。当前基线不授予无人审批的通用生产权限。

### 10.4 恢复与数据变更

发布前有明确失败处理、回退或前向修复路径。自动恢复只执行已批准、适用条件明确的预案，不能临时自由选择高风险操作。

数据库迁移另有数据安全和恢复考虑。撤回代码不被视为恢复数据的等价操作。具体部署形态、迁移策略及恢复目标在选定试点项目后确定。

### 10.5 交付后维护

代码合并后继续跟踪实际发布与验收。维护任务可来自运行故障、用户反馈、安全与依赖问题、费用、文档和技术债，而不是强制重新包装成产品需求。

严重故障时可以暂停非必要新功能，转入恢复工作；对应触发标准和授权政策待定。项目应能暂停、恢复和退出，不能无限生成维护任务维持活动。

## 11. 数据、审计与外部动作一致性

### 11.1 最小持久化对象

这是概念模型，不是最终表结构。

| 对象 | 核心内容 |
|---|---|
| 项目 | 仓库、目标分支、责任、规范和政策引用 |
| 需求及版本 | 原始输入、分析、确认、变更与任务关联 |
| 任务及版本 | 契约、依赖、责任、状态与累计预算 |
| 人、节点、Agent | 身份、归属、能力与授权关系 |
| Run | 执行归属、代次、租约、基线、环境、开始结束和结果 |
| 范围授权与资源占用 | 任务／Run、授权版本、路径或资源、审批、有效状态 |
| 决策与批准 | 请求、依据、允许范围、批准主体和关联版本 |
| 集成候选 | B/H/M/C、差异、门禁结果、主线更新状态 |
| 测试与产物 | 验证对象、环境、结果、证据引用和保留信息 |
| 发布 | 指定产物、环境、批准、执行和健康结果 |
| 审计事件 | 操作者、前后状态、版本、理由、因果关联 |
| 待发送消息／待执行操作 | 幂等标识、投递或执行状态、重试和对账所需引用 |

数据库服务于中心协调，远程节点通过 API 访问。优先评估中心本地 SQLite；具体数据库选择仍待定，不要求第一版引入独立消息代理、缓存集群或完整事件溯源架构。

### 11.2 事务与消息投递

状态变更、审计事件和待发送通知在同一事务中保存，再由发送器投递。确认丢失或进程重启可以导致重发，接收与处理必须幂等。

对执行命令进行授权时检查当前任务版本、Run 归属和分配代次。合法身份发送的过期请求，也必须拒绝或转为历史记录。

### 11.3 外部动作与恢复对账

Git 更新、部署和其他外部系统动作不被假定为与本地数据库原子提交。需要稳定操作 ID、执行回执、可重试策略和恢复对账。

例如：主分支已更新，但中心在记录成功前崩溃。恢复后根据操作和代码引用核实实际状态，补齐记录；不能盲目再执行一次，也不能断言之前失败。

对外部动作区分可安全重试、必须先查询结果和需要人工核实。系统不承诺所有分布式副作用天然“恰好一次”。

### 11.4 审计、保留和退出

审计保留决定、授权、实际动作和证据，不需要把所有聊天永久保存为项目事实。敏感内容脱敏；大日志和产物可独立存储，由数据库引用并设置保留策略。

备份、恢复与导出是基线能力。导出应让人和新的开发会话取得需求、任务契约、决策、代码引用及关键证据，不被中心数据库内部格式锁死。

如果试点采用外部 Git／CI／产物平台，明确哪些数据只保存引用、哪些必须备份，不能把链接存在等同于证据永久可用。

<a id="s12"></a>
## 12. 自主推进、预算、暂停与安全边界

### 12.1 推进循环

```text
读取当前权威状态
  → 检查暂停、严重故障、授权、预算与节点可用性
  → 找到依赖满足且范围可用的任务
  → 原子领取并建立本次执行授权
  → 执行、验证、保存检查点和证据
  → 进入集成、返工、阻塞或待决状态
  → 更新后续依赖；仍有已授权工作时继续
```

任务就绪、前置完成、评审或测试结果、范围申请、节点状态改变等事件触发处理。定时检查用于补漏和维护，不以持续调用模型轮询状态为默认方式。

### 12.2 预算和循环控制

预算覆盖单次 Run、单任务跨重试与跨角色执行，以及项目周期总量。新建 Run、拆出修复步骤或更换 Agent 不能自动清零已使用预算。

修复、评审和冲突协商均有上限，达到上限后暂停并形成明确决策请求。具体时间、费用、调用和次数阈值不在本基线中设定。

费用限制能否成为硬上限取决于适配器的计量和中止能力；如果只能事后统计，必须标为软限制，不能宣称能够精确封顶。实现方式见 U11。

心跳只说明可联系；有效进展需要提交、测试结果、确认的决策或解除阻塞等证据。衡量推进不以消息条数、代码行数和 Agent 活跃时长为主。

### 12.3 决策请求

需要人判断时，提交问题、已验证事实、可选方案、推荐意见、风险与等待期间允许执行的动作。

人的沉默不是同意。没有事前授权的安全默认动作时保持等待；其他互不依赖、已授权的工作可以继续。

相同未变化问题应汇总和去重，不能持续创建任务或重复提醒。

### 12.4 暂停与撤销

项目暂停后停止新派单，阻止未批准的后续高风险动作，并向在线 Runner 发送取消或暂停要求。受管进程按执行器能力终止并留下检查点。

无法承诺立即终止离线设备上的进程。中心通过撤销租约／授权、拒绝迟到请求，以及不向开发端提供主线和生产高权限，限制旧执行的后续影响。

暂停、取消、执行失败和节点离线分别记录。修改任务负责人不等于已经停止旧运行。

### 12.5 安全不变量

- 身份从认证确定；正文中的 ID 和模型声称的权限不构成授权。
- 每个动作同时校验主体权限、项目范围、任务授权和当前执行归属。
- 开发执行端不能绕过集成入口直接写受保护主线，不能自行批准生产发布。
- 规范文件和模型角色不是安全沙箱；路径检查也不等于对系统命令、网络和凭据的全面隔离。
- 密钥不进入共享规范或普通日志；测试代码与高权限控制凭据分离。
- 模型生成的完成报告、协商结果和测试结论必须由实际证据支持。

系统对本地操作系统管理员、恶意团队成员和被攻陷节点的防御程度尚需通过信任模型明确，不能默认为本平台能控制所有私人电脑上的行为。

<a id="s13"></a>
## 13. 端到端流程与异常路径

### 13.1 正常交付

1. 人提出需求，系统保留原始记录。
2. Requirement 角色分析、查重、澄清并形成版本化方案；必要时先做有界验证。
3. 人或既有授权机制确认目标、范围和预算，形成可执行任务及验收条件。
4. Leader 提出依赖与分派方案，中心检查权限、范围、容量和预算后领取任务。
5. Runner 准备任务分支、隔离环境及固定上下文，启动开发工具。
6. 成员在授权范围内实现和自测；越界需求先申请，阻塞先报告。
7. 提交固定代码版本、自测证据和交接材料，进入集成队列。
8. 集成控制器在当前主线上生成实际候选，独立检查范围、测试与必要评审。
9. 门禁通过且版本仍有效时更新主线，记录真实集成结果。
10. 对固定发布物完成验证、授权、部署和健康检查。
11. 完成交付验收；故障、反馈或新需求按性质进入下一轮。

### 13.2 必须覆盖的异常路径

| 异常 | 应有行为 |
|---|---|
| 输入不清楚或假设未验证 | 留在分析／验证或待决阶段，不直接启动大范围开发 |
| 范围与在途任务冲突 | 等待、调整计划或审批扩展，不让双方同时获得互斥授权 |
| 任务失联后旧结果迟到 | 保存证据但拒绝过期执行修改当前状态或放行 |
| 自测失败 | 在原任务预算内修复；达到上限升级，不绕回新需求重置预算 |
| 文件可合并但行为不兼容 | 候选验证阻断，分析契约和决策后返工 |
| 候选验证期间主线变化 | 作废对应放行条件，重建并重新验证 |
| 合并或发布动作结果不明 | 查询实际外部状态并对账，不盲目重试 |
| 中心重启 | 从数据库恢复，核对有效执行、未投递消息和外部动作 |
| 模型会话丢失 | 从版本化上下文与事实恢复，不依赖历史会话继续存在 |
| 发布后健康异常 | 执行已批准的止损／恢复路径，记录事故与修复任务 |

<a id="s14"></a>
## 14. 实现顺序与系统验收

### 14.1 三阶段落地

| 阶段 | 主要内容 | 目标 |
|---|---|---|
| A：受控协作 | 人工建任务、两个执行端、基础身份、任务级分支、范围检查、单一集成入口、必要验证和审计 | 先证明并行开发不会绕过控制进入主线 |
| B：自主推进 | Requirement 与 Leader 按需调用、依赖与范围申请、上下文组装、预算、恢复与决策请求 | 在授权内连续推进，不无限重试、不扩张目标 |
| C：交付维护 | 测试分析、发布授权与执行、发布后反馈、维护与完整恢复演练 | 从需求走到真实交付与持续维护 |

第一阶段开始就保留阶段 B/C 所需的任务和证据关联，但不要求先实现全部自动化。备份和基本恢复随核心数据一起建设，不推迟到最后才补。

### 14.2 验收场景

| 编号 | 场景 | 必须达到的结果 |
|---|---|---|
| A01 | 两个节点同时领取同一任务 | 只有一个有效归属；另一方收到明确结果 |
| A02 | 同一派单或提交请求重发 | 不产生重复任务执行或重复业务副作用 |
| A03 | 旧 Run 失联后任务重新分派 | 旧 Run 恢复不能覆盖新状态或触发放行 |
| A04 | 两个任务申请同一互斥范围 | 不出现同时有效的冲突授权；有等待或决策路径 |
| A05 | 实现者越界修改并漏报文件 | 中心从真实差异发现，拒绝集成 |
| A06 | Agent 宣称测试通过但无可信执行证据 | 不能通过相应门禁 |
| A07 | 自测后主线更新 | 针对实际新候选执行验证，不直接沿用旧结论 |
| A08 | 候选排队期间分支又有新提交 | 旧候选仍绑定原版本，新版本不能偷渡 |
| A09 | 修改 CI 或删除测试以获得通过 | 触发受保护规则审查，不能自行降低标准 |
| A10 | 主线更新成功但中心随后崩溃 | 恢复后识别已完成动作并补齐记录，不重复合并 |
| A11 | 预算耗尽、循环超限或项目暂停 | 停止后续自动推进，不通过换 Run 绕过限制 |
| A12 | Leader 或成员会话完全丢失 | 新会话能从仓库、状态和检查点接续 |
| A13 | 发布批准后主线继续变化 | 只部署获批的固定对象，不部署新的浮动版本 |
| A14 | 私人开发端尝试生产操作 | 无对应凭据或授权，不能通过平台执行 |
| A15 | 从备份恢复或导出接手 | 能恢复需求、任务、决策、代码引用和必要证据，并核对外部状态 |
| A16 | 一个真实功能从需求进入系统 | 能追溯到验收与发布；不会把合并等同于交付 |

是否“工业级”以这些行为在选定部署和信任边界中被验证为准，不以角色数量、功能菜单或演示中的成功执行次数判断。

## 15. 尚未确定的事项

以下条目不是已确认能力，也没有隐含默认授权。确定后更新相应设计章节及决定记录。

| 编号 | 待决问题 | 当前约束／候选方向 |
|---|---|---|
| U01 | 首期项目形态、仓库模型和试点场景 | 当前按单项目、单仓库、单主分支设计；具体语言、测试、部署形态未定 |
| U02 | 人机授权矩阵与信任边界 | 不允许模型自行放宽门禁；哪些需求、范围、合并、发布可以自动批准未定；恶意节点防御范围也未定 |
| U03 | 执行模式与首个适配工具 | 支持交互与托管两类语义；首期做哪一种、先适配 Codex 还是其他工具待定 |
| U04 | 中心与可信验证的部署位置 | 中心可与成员同机或独立；是否设专门常在线验证／发布节点待定 |
| U05 | 执行隔离和密钥管理 | 必须明确强制控制与能力降级；容器、虚拟机、系统沙箱或其他方式及密钥存储待定 |
| U06 | 路径授权与共享资源占用策略 | 任务级授权已定；粒度、热点列表、待合并占用、超时、扩展与死锁处理待定 |
| U07 | 测试、评审与发布政策 | 固定最低门禁已定；全量条件、可信证据、人工批准、恢复要求待定 |
| U08 | 技术栈、数据库与状态模型 | 优先评估本地 SQLite；具体语言、框架、表结构、任务／Run 枚举与迁移方案待定 |
| U09 | API、MCP 工具和网络协议细节 | 星型、认证与幂等语义已定；优先考虑 HTTPS API＋长轮询；协议版本、字段、传输和组网产品待定 |
| U10 | Git 托管与精确集成方式 | 任务级分支、固定候选和受控主线入口已定；托管服务、PR 是否必需、合并策略、凭据与条件更新待定 |
| U11 | 并发、预算、租约、重试与离线政策 | 必须有界且跨 Run 累计；具体数值、费用计量、离线是否继续纯本地编码、接管时机待定 |
| U12 | 上下文、规范和工具配置形式 | 外部持久化与版本化已定；文档结构、管理区块、装配方式、适配器重载规则待定 |
| U13 | 审计保留、备份、导出与运行界面 | 必须可追溯和恢复；保留周期、脱敏规则、产物存储、导出格式和首期界面待定 |
| U14 | 冲突修复与人类责任分配 | 唯一落地者、决策留痕和预算上限已定；默认修复者、升级规则与替代审批人待定 |

建议先确定 U01–U05 的实际场景、授权和执行边界，再细化任务契约、范围授权与集成状态机；随后由这些约束推导表结构、API 和 MCP 工具。不要先写通信报文，再倒推系统职责。

此前提到的“两个自动修复轮次”“某个固定并发数”“特定维护比例”等示例数值，不作为本设计基线的最终政策。

### 16.2 后续讨论如何进入基线

每个待决事项确定后，记录决定、理由、适用边界和影响章节。改变已确定决定时，应明确替代关系，不静默修改旧约束。

模型可以提出流程改进，但不能自动修改自身的授权、预算或验收规则。流程配置和相关程序变更同样需要版本化与验证。

下一版详细设计应首先冻结任务契约、权限／范围模型和集成状态机，再形成最小数据结构、接口与开发任务。本文不直接作为开放式“把整个平台一次开发完”的任务。

---

**设计基线摘要：** 共享双池组织工作，单中心维护事实，Runner 管理执行，MCP 提供受限工具，任务级隔离减少干扰，范围与契约预防冲突，实际候选验证控制集成，受控程序落实发布；Agent 做判断和实现，但不能自己宣布规则已经满足。
