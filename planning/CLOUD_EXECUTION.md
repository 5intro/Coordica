## 每个 PR 的闭环

1. 选择一个已满足依赖的工作包，固定最新输入 SHA、需求版本和范围；使用 `codex/` 分支。
2. 实现聚焦改动，补实际失败场景回归。输出测试命令、退出码、环境和停止/清理证据。
   先跑受影响测试及原生 lint/build/typecheck；涉及契约则检查生成漂移；交接运行 `make quality`。
   提 draft 前在云端工作区完成可执行的受影响验证和质量检查，不能把首次基本自测留给 CI。
   无法执行的完整项按实际原因保留阻断，依第 3 步进入 draft/远端验证，不伪造本地通过。
3. 受影响检查与质量通过后可创建 draft PR，描述行为、范围、实际验证和未实测/环境阻断项。
   文档片按质量及必要链接检查；代码片按适用回归/build/lint/契约漂移。完整门禁阻断不冒称通过，draft 不授予合并。
   修复更新同一个 PR，不复制 PR 或重复业务批准；本恢复批次线上操作由父会话完成。
4. 在该 PR 明确触发 `@codex review` 与 `@codex security review`，保存触发评论及回应身份/时间。
   更新 head 后核对是否新审；未自动新审时可重触发，采用有界间隔，不刷评论或绕过额度。
5. 读取最新 head 的全部三平台 CI、代码审查、安全审查和未解决意见。修复可行动问题，补回归，再自测后推送原 PR。
   每轮记录新 head；旧提交通过不继承。优先处理 P1，不靠文案/删除测试掩盖问题。
6. 所有门禁明确通过后，重读 PR 当前 head、base/mergeability 和未解决意见，按固定 head 合并。
   target main 更新影响验证时重新校验；按依赖顺序合并，不降低保护规则或跳过既定审查。
7. 保存 merge SHA、PR 和证据摘要，更新 ROADMAP 同一任务行及 PROGRESS，再开始下一包。

本地 source、手写 fixture、局部回归、本地只读 review、正式 GitHub 审查、三平台 CI 和真实 harness 必须分开记录。
当前本地 mcpconfig 因中立 Git 临时目录前提阻断；允许 draft 获取正式审查和真实 CI，不删除标记或跳守卫。
即使远端完整 CI 覆盖了相应场景，本地仍记录“未跑/阻断”，不能改写成“本地全仓通过”；未覆盖或未通过的门禁仍阻断合并。

“审查已结束”与“明确无问题”分开。仅有 null 字段或汇总、没有覆盖当前候选的明确回执/可读报告，
以及额度不足、超时或 Failed，均不能当作通过。报告不可读时不得声称读到报告，也不能猜测零发现；
须核对是否另有绑定准确 head 和实际审查内容的独立明确回执。base 引用变化时检查实际树、完整差异及适用政策，
不同 head/内容不能继承旧通过；同一 head/相同审查输入的覆盖关系需记录证据，不能只按时间或 mergeable 判定。
只存在既有私人可信主机边界时保持原已接受风险记录，不能标成已修复；新风险不得自动套用旧风险豁免。
没有可核实的当前内容明确结论就保留阻断，不自行提交批准 review 代替独立审查。
CI 平台只在真实 job 通过后标通过；交叉编译、fixture 和真实 harness 验证分别记录。
