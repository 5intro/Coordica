# 云端实施批次与审查闭环

日期：2026-11-02（Asia/Shanghai）。需求基线 R2026-11-02.3。
任务主表仍为 [ROADMAP](../ROADMAP.md)，实施证据追加到 [PROGRESS](PROGRESS.md)。
本文件是同一组 C 任务的工作包和操作约束，不建立第二套任务状态表。

## 本轮授权与边界

Owner 本轮要求：多准备任务，创建并绑定仓库的云端环境，使用 `gpt-6.1-sol` / `ultra`，
派发云端开发，自测后提 PR，触发自动审查、修复，再在门禁通过后合并；定时观测直到合并才删除。

据此执行本批 C01–C08 的云端实现与离线回归；C09–C12 只先准备细化工作包，不能跳过阶段依赖。
与旧文档“尚无新方向实施授权”冲突的表述，以本轮记录的准确范围为准。
真实 harness 订阅消费、原生登录/凭据迁移、正式中心运行、配对、实验、安装包发布和本机升级不在本批范围。
C07/C08 可以分别交付离线适配 PR；未取得真实验证时，父任务保持待验证，不能据 mock 标记完成或越过阶段出口。
正式中心保持暂停，自动派发关闭；云端开发不是让 Coordica 自己启动业务任务。

## 环境与模型

- 仓库：`https://github.com/5intro/Coordica`，从当时最新 main 加上本批规划分支接收需求。
  不继承陈旧本地 main，不上传 `.coordica*`、私人 `docs/`、登录目录或生产数据。
- 可复用的专用 Codex Cloud 环境；默认仅本人可用，绑定本仓库。
  环境配置复用不等于永不停机的服务器；每个任务有自己的工作文件和安装状态。
- 明确指定 `model=gpt-6.1-sol`、`thinking=ultra`。目的环境不支持时记录阻断，不静默换模型或降低强度。
- 使用云端原生 Codex，不通过嵌套 CLI/模型包装器驱动开发；Claude/dsh/Antigravity 不参与本仓库实现。
- 依仓库 CI 准备 Go 1.27.2、Node 24、Python 3.12、Git 和受限仓库操作能力；依赖从官方来源安装。
  先检查资源、磁盘、网络策略和工具版本；共享数据/端口/临时输出独立，不复制本机的认证文件。
- 安装/启动脚本不调用模型、不启动正式中心、不在环境发布时自动跑业务。
  普通回归显式关闭 live opt-in；不得为解决依赖访问而偷偷关闭 TLS/网络安全策略。
- 缓存依赖可复用；临时测试目录、进程和日志有界。使用已有监督测试脚本，不并发启动无界全仓 race 套件。

## 每个 PR 的闭环

1. 选择一个已满足依赖的工作包，固定最新输入 SHA、需求版本和范围；使用 `codex/` 分支。
2. 实现聚焦改动，补实际失败场景回归。输出测试命令、退出码、环境和停止/清理证据。
   先跑受影响测试及原生 lint/build/typecheck；涉及契约则检查生成漂移；交接运行 `make quality`。
   提 PR 前在云端自己的工作区完成适用验证，不能把首次基本自测留给 CI。
3. 提 PR，描述行为、范围、验证与未实测项；修复更新同一个 PR，不复制 PR 或重复业务批准。
4. 在该 PR 明确触发 `@codex review` 与 `@codex security review`，保存触发评论及回应身份/时间。
   更新 head 后核对是否新审；未自动新审时可重触发，采用有界间隔，不刷评论或绕过额度。
5. 读取最新 head 的全部三平台 CI、代码审查、安全审查和未解决意见。修复可行动问题，补回归，再自测后推送原 PR。
   每轮记录新 head；旧提交通过不继承。优先处理 P1，不靠文案/删除测试掩盖问题。
6. 所有门禁明确通过后，重读 PR 当前 head、base/mergeability 和未解决意见，按固定 head 合并。
   target main 更新影响验证时重新校验；按依赖顺序合并，不降低保护规则或跳过既定审查。
7. 保存 merge SHA、PR 和证据摘要，更新 ROADMAP 同一任务行及 PROGRESS，再开始下一包。

“审查已结束”与“明确无问题”分开。发现字段 null、只有旧汇总、私有报告不可读、额度不足、超时或 Failed
均为未确认/失败，不能当作通过。只存在既有私人可信主机边界时保持原已接受风险记录，不能标成已修复；
新出现的风险不得自动套用旧风险豁免。没有获得原始报告就记录阻断，不猜测已无问题。
CI 平台只在真实 job 通过后标通过；交叉编译、fixture 和真实 harness 验证分别记录。

## 定时跟进与续工

Owner 已纠正监控归属：由正在施工的云端 Agent 在自己的工作会话中创建并维护定时续工，
不能挂在派发者/当前本地对话上，也不能用全局巡检代替施工 Agent 的闭环。
该会话检查自己负责的 PR，读取审查结果、修复、自测、更新原 PR，并在固定 head 门禁全过后合并。
默认建议每 20 分钟检查，不为轮询新开会话，不在自己正忙时重复派相同修复。
未来有多个施工会话时，各自维护自身任务及 PR 的定时续工，不建立一个全局替代监控。

环境和施工会话尚未创建时不创建监控。派发指令必须要求施工 Agent 先确认自己具备云端定时/唤醒能力，
并记录实际定时任务与自身 thread/host 的绑定；只写进提示词不算定时已生效。
若目的环境不提供该能力，明确报告阻断，不悄悄改成本地 heartbeat、全局任务、shell 常驻轮询或 sleep 循环。
派发者不在自己的对话设置轮询来模拟这一能力，也不承诺本机关机后本地工具仍可用。

监控的持久清单包含：批次范围、C 任务、云端 thread/host、PR、当前 head、CI/代码/安全状态、
触发评论、已处理意见标识、最近观测和 merge SHA。状态变化在 PROGRESS 或受控检查点留痕，不能只存在模型记忆。
清单是执行证据，不是另一套任务状态机；任务状态仍只更新 ROADMAP。

- 尚未发布专用环境：不创建任何监控；不占用别的项目环境，不伪造已派发。
- 配置就绪：按原授权启动一个 `gpt-6.1-sol` / `ultra` 云端会话，传入本文件、规划分支和固定 SHA。
  首轮要求确认仓库/版本/模型及范围，并由该施工 Agent 建立自身定时续工，再推进 C01；保存真实 thread/host/监控归属。
- 新可行动审查意见或 CI 失败：施工 Agent 在原会话中去重、修复、补测并更新原 PR；无变化不反复报告。
- 审查额度/权限阻断：保留未确认状态并报告，不靠盲目反复重触发或修改门禁解决。
- 单个 PR 关闭但未合并不是成功；没有 PR、worker 空闲或一次运行结束也不是本批完成。
- 只有本施工会话负责的 PR 全部确认 merged，且没有遗留应提交的改动/修复，才由施工 Agent 删除自己的监控。
  单会话负责整个批次时不能因为首个规划 PR 合并而提前停止；C07/C08 的真实验证缺口仍留在父任务状态。

目前环境、云端会话、PR 号、监控 ID 以 [PROGRESS](PROGRESS.md) 的最新批次记录为准；
未填写的字段为尚未完成，不据本方案推定资源已经创建。
