# 任务与待处理：底座和应用视图的边界

日期：2026-11-02。当前基线 R2026-11-02.4；R92 的来源投影边界继续保留，首版范围由 R93–R98 收紧。
面向用户统一称“任务”和“待处理”；“阻断”仅保留为具体原因或计划状态，不作为产品池名称。
本次授权更新规划；具体字段与路由仍是实施草案，不代表已删除现有数据、页面或门禁。

本批只做聚合底座。任务/请求查询与最小诊断客户端足以验证控制层；不先做业务 UI 或迁移上层应用。
下文业务流程仅解释边界，不是本批任务。保留原生输入、审批、单写和停止保护，不以缩小产品范围删掉必要可靠性。

## 已确认边界

底座保留通用 Task 调度、运行事实、待处理请求和恢复条件；池是这些事实的查询/界面投影。
需求池、业务审查池归上层应用。底座提供“任务”和“待处理”两类最小运行视图，不承担完整业务工作台。
任务驱动需要持久任务及其调度能力，不能把它们全部移到每个上层重新实现。
“两个池”描述导航，不意味着系统只剩两种实体或两张数据库表。

| 概念 | 底座保留 | 上层应用拥有 |
| --- | --- | --- |
| 需求池 | 无独立业务 Requirement 实体；接收已授权任务及 external_ref | 需求收集、去重、排序、验收条款及是否拆任务 |
| 任务池 | Task 生命周期、执行队列、依赖、Run、取消与恢复；列表/过滤接口 | 业务目标、任务模板、业务优先级政策及完整任务 UI |
| 审查池 | 把审查 Agent 作为普通任务执行，返回结果/产物事实 | 审查标准、结果是否合格、候选、合并/发布和业务批准 |
| 待处理 | 原生 PendingRequest、失败事实、调度等待原因、停止未知及可用恢复操作 | 业务阻断、负责人/期限/升级规则、跨来源待办汇总及 UI |

上层业务任务可关联一个或多个底座 Task；底座 Task 是执行工作的事实来源，上层业务状态不与它逐字段双写。
例如底座“审查任务执行成功”不意味着上层“审查通过”；失败报告也不能仅被 UI 清除后变成成功。

## 用待处理视图取代统一阻断状态机

不要创建一份与 Task、Run 和 PendingRequest 各自状态并列的万能 Blocker 状态机。
优先复用各来源记录，按任务聚合只读 attention 投影。必要时可持久化该投影用于分页，但必须可重建。
任务可以同时有多个原因；任务仍保留在任务列表，待处理视图链接回它，不把任务在池之间搬移。

| 类型 | 是否默认要求人工 | 恢复依据 |
| --- | --- | --- |
| 等依赖、正常队列、已知额度重置时间 | 否；一般显示在任务详情 | 已配置条件满足且当前授权有效，幂等唤醒 |
| 原生问题或工具许可请求 | 是，按实际响应主体和权限 | 请求 ID、版本、会话绑定及原生答复确认 |
| 认证失效、工具配置错误 | 常需人工/管理员 | 实例修复并重新探测；不点一次“解决”就宣称恢复 |
| 失败且自动重试耗尽 | 按策略需要决策 | 保留失败 Run；显式重试创建新尝试，不重写旧结果 |
| 停止未知、外部副作用未知 | 需要核对，但不等于已确认失败 | 实际进程/协议/外部证据对账；不能凭自由文本清除 |
| 上层“等待法务/发布批准” | 由上层决定 | 上层持有业务确认；底座仅承载已注册 hold 或尚未提交的后续任务 |

PendingRequest 是需要具体回答的持久请求；排队原因是实时条件；终态失败是历史事实。
这三者不能都塞进一个 status=blocked，也不能把所有 waiting 强制展示为“等人审批”。
等待业务批准时，上层可以先不提交发布任务；确需保留排队任务时，用具名上层 hold，
由该应用在自身权限内通过版本化命令释放。底座不解释“法务批准”是否成立。

投影建议字段：origin_kind/id、task/run/instance 关联、reason_code、requires_action、
allowed_actions、expected_version、evidence_ref、observed_at。allowed_actions 仅辅助展示，执行时仍重验权限。
节点/实例级问题可影响多个任务，但不应为每个任务复制一份可独立“修复”的账号故障状态。
每次点击处理都路由到具体用例：respond_request、retry_task、refresh_instance、reconcile_run 或 release_hold。
不提供绕过这些前置条件的统一 resolve_blocker=true。
即使两个视图同时打开、事件重复或到达延迟，唯一事实记录及版本检查仍决定状态。

## 与 DeepSeek 原型的对应

参考固定提交 `6337fc823ce20251c8de8085948165c81aaa701e`：

- [领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/001-domain.md)
  将 Ticket 与 Assignment 分开，将 Attention 用于人工问题；无需先建立业务需求池才能执行任务。
- [stage.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/stage.ts)
  根据 Ticket、最新报告、Attention 和送达问题推导 person/working/idle/ended 视图。
  借鉴“从事实推导待处理”的做法，不复制其 ready→待审查等开发业务分类。
- 原型的 Source、Eval、Mandate、Ticket、Assignment 是一套应用结构，不应整套变为底座强制模型。
  来源和业务接单研判在上层，授权边界、任务和执行事实在底座；程序提交仍无需模型先评估。

T3 继续用于会话/交互适配参考；DeepSeek 用于任务推进和人工介入投影参考。
是否需要需求管理、人工审查或群聊，由上层自行选择，并不成为使用底座的必选功能。

## 示例：修复问题并发布

开发应用接收需求，提交修复 Task A；底座选择节点与 harness 执行。
A 的原生端请求权限时，底座持久化 PendingRequest，出现在待处理视图；回答后继续 A。
开发应用读取 A 的产物和执行结果，决定提交审查 Task B。B 对底座仍是普通 Task。
开发应用依据审查证据决定是否允许发布，再提交 Task C 或释放其业务 hold。
底座只保证 A/B/C 按当前授权可靠执行；合并、发布规则不进入通用调度器。
底座最小运行 UI 采用任务与待处理两个主入口，同时在任务详情展示上层自定义阶段。

## 规划落点（已纳入任务表）

- C02/C11/C13：保留任务事实和执行队列；不因移除池页面而删掉调度、依赖或权限机制。
- C06/C12/C14：保存原生请求、错误、恢复与限额事实，作为待处理查询的数据源。
- C15/C17：提供按权限过滤的任务与待处理投影，支持 headless 客户端；不维护第二套业务状态。
- C16：需求/审查页面与实体移入开发应用；隐藏或合并入口不等于删除验收、候选或历史证据。
- V17 验证：一任务多项待处理；同一实例故障影响多任务；正常等待不生成误导审批；
  旧请求处理不能恢复新 Run；关闭待处理卡片不能解除实际条件；移除需求/审查页面后通用任务仍可执行。

R92、V17 和 ADR-009 已记录本次决策。具体布局可在 C17 调整，但不能重新把业务池设为底座必选功能。
C01–C18 的实施状态保持规划中；功能迁移、删除和真实执行不因本次规划确认而自动开始。
