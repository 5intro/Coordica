## 定位与边界

1. Coordica 是连接不同原生 harness 的基础设施，统一提供接入、会话、执行、调度和运行管理能力。
2. 底座服务于多个上层应用，包括开发任务、个人助理和公司信息管理，但不内置这些业务的具体实现。
3. 复用原生 harness 已有的推理、工具调用、上下文管理和执行机制，不重新实现一套通用 agent 循环。
4. 支持使用原生 harness 官方允许的订阅登录与额度；不抽取订阅凭据反代成通用模型 API。
5. 能力与额度受原服务支持范围限制，不能把“已接入”理解为完整继承或无限调用。
6. 底座不绑定某个模型、厂商、任务类型或前端。
7. 上层业务通过明确接口使用底座，不能依赖底座内部数据库或直接操纵内部状态。
8. 底座自身可提供必要的配置与诊断界面，但不承担完整的业务工作台。

## Harness 接入与能力复用

9. 保留并完善现有协议适配器，优先使用官方支持的程序接口。
10. 支持增加新的 harness 适配器，避免在核心调度逻辑中到处判断厂商名称。
11. 区分 harness 类型、已配置实例、认证配置、模型和执行节点。
12. 同一种 harness 可以配置多个实例，但不能假定实例之间账号和状态天然隔离。
13. 明确区分已安装、版本兼容、已认证、能力可用和实际调用成功。
14. 能力声明采用支持、不支持、未知或有条件支持，避免用单个“在线”状态代替全部事实。
15. 动态发现模型与配置选项；无法发现时允许显式配置，并标明未验证状态。
16. 支持在原生接口允许时选择模型、推理强度和执行模式。
17. 能力不支持时明确返回原因，不静默降级、换模型或换 harness。
18. 按 harness 的机制复用 skills、MCP、工具与配置，并记录实际生效范围。
19. 对浏览器、Computer Use、图像等特殊能力单独验证，不以模型支持代替工具可用性。
20. 保留协议特有能力的扩展入口，不能为追求统一接口而丢失重要原生功能。

## 会话与双向交互

21. 同时支持一次性任务执行和持续多轮会话。
22. 提供创建、读取、恢复、发送消息、停止和释放会话等适用操作。
23. 区分排队消息、运行中补充信息和立即中断；按 harness 能力明确实现。
24. 处理原生提问和权限请求，并支持将回答回传到正确的会话与请求。
25. 待处理请求有唯一标识、状态及适用范围，支持重连后继续处理。
26. 过期、取消或所属执行已结束的请求不能被错误地再次批准。
27. 会话恢复与任务重试分别建模，避免把恢复上下文误当成重新执行。
28. 明确区分取消当前轮次、结束会话与取消整个任务及其子任务。
29. 保留 Coordica 标识与原生 Session ID 的映射，支持定位问题和关联记录。
30. 统一接口之外可保留原始事件用于诊断，但不能靠解析自然语言判断关键状态。

## Agent 与调度机制

31. 提供 agent 配置与运行实例的基础抽象；角色名称、职责内容由上层定义。
32. 允许上层为 agent 指定 harness、执行配置、工具范围、上下文和节点要求。
33. 支持主控向执行 agent 分派任务，也支持程序直接提交任务。
34. 主控可以运行在原生 harness 中，不要求引入额外模型 API 框架。
35. 支持父子任务关联、并行执行、依赖等待、结果汇总和取消传播。
36. 支持队列、并发限制、超时与有界重试，避免无限派生和重复执行。
37. 区分逻辑 agent、任务、一次运行和原生会话；它们不是一一对应。
38. 每个执行单元有明确的调度归属，防止上层、底座和 harness 内部重复派工。
39. 若允许 harness 原生子 agent，尽可能关联其执行事实；无法观测时明确标示。
40. 不把底座做成理解所有业务的万能流程引擎；先提供上层确实需要的调度原语。
41. 上层负责定义“先审查再发布”等业务阶段；底座负责按授权执行对应操作。
42. 支持优先级与节点选择，但不要在未经配置时自动改变模型质量要求。

## 事件、状态与恢复

43. 输出结构化事件，包括执行开始、输出更新、工具活动、待处理请求、失败和结束。
44. 事件应可关联任务、运行、会话、agent 和节点。
45. 支持持久记录、断线后补取及重复事件识别。
46. 不能将前端断开连接等同于取消后台执行。
47. 服务重启后应识别哪些执行可恢复、仍在运行或状态未知。
48. 提交重试需要避免重复启动任务，尤其是具有外部影响的操作。
49. 明确区分成功结束、失败、中断、取消、等待人工和无法确认。
50. 底座报告执行事实；业务上的“验收通过”“已上线”“已发布”由上层根据证据判定。
51. 保留失败原因与恢复建议，不用一个笼统的“执行失败”掩盖认证、额度、协议和工具问题。

## 权限与人工介入基础能力

52. 将原生工具权限请求、上层业务确认和任务授权分别表示，不能混用。
53. 底座负责请求传递、授权边界与结果记录；上层决定审批界面的业务呈现。
54. 人工决策关联具体请求及必要的版本信息，不默认适用于后续变化。
55. 不能把普通 agent 的回复当作用户授权。
56. 执行权限不得因委派、恢复或切换节点而扩大。
57. 原生协议不支持所需审批时，明确限制或提供受支持的回退路径，不能伪造成功。
58. 不将中心管理权限与其他应用凭据无差别注入所有执行者。
59. 等待人工不应阻塞无依赖任务，也不应丢失待处理请求。

## 多节点与额度管理

60. 继续采用中心与执行节点分工，明确每项任务实际在哪台机器运行。
61. 路由时考虑节点在线情况、harness 实例、实际能力和并发容量。
62. 不默认跨机器共享登录、文件、会话或工具权限。
63. 支持远程接入与连接恢复；具体部署和网络方式可以独立配置。
64. 展示真实心跳与运行状态，历史上报不能永久代表在线。
65. 能获取时记录原生用量、限额及重置时间；无法获取时显示未知，不自行估算成事实。
66. 支持因额度不足等待或暂停；切换账号、模型或 harness 必须遵循显式策略。
67. 不提供绕过原厂限额或把多个订阅伪装成无限统一 API 的机制。

## 上层扩展接口

68. 对外提供稳定、版本化的任务、会话、事件、能力和待处理请求接口。
69. 上层可使用自己的 UI、存储和业务实体，通过引用关联底座的任务与运行记录。
70. 提供扩展接入上下文、工具及结果的方式，但不要求底座理解这些内容的业务含义。
71. 角色群聊由上层决定成员、发言和讨论规则；底座提供消息送达与执行支持。
72. 开发工作台由上层实现代码审查、候选集成、测试和发布规则。
73. 个人助理由上层实现偏好、日程、资料收件箱及长期事务。
74. 公司信息管理由上层接入飞书、企业微信等服务并维护业务权限与数据映射。
75. 文章库、素材库和内容发布不是底座的核心实体。
76. 公司记忆和项目知识由上层或独立服务维护；底座提供上下文传递及引用能力，不负责决定什么应成为长期知识。
77. 已有开发专用逻辑可以继续保留为应用模块，不必为了抽象一次性删除或重写。
78. 新扩展应有清晰的注册和兼容机制，不要求每增加一个业务就修改底座核心。

## 验证与实施顺序

79. 先审计最新源码，明确已有能力、已声明未验证能力和实际缺口。
80. 第一优先级是持续会话、运行中消息、原生提问与审批回传，以及完整事件链路。
81. 第二优先级是统一能力发现、实例配置、节点路由和恢复机制。
82. 第三优先级是稳定上层接口，再逐步分离已有开发业务。
83. 先选择少量 harness 做完整接入验证，避免“支持很多，但都只能跑一句提示词”。
84. 对每种 harness 验证启动、继续交流、取消、恢复、待人工和限额等行为。
85. 检查原生工具是否真实可用，而不只检查工具名称是否出现在列表中。
86. 用开发任务与非开发任务各验证一次，证明底座没有把 Git、代码提交或测试结果写成所有任务的必要条件。
87. 对断线、重复提交、迟到结果、重启和过期审批建立针对性验证。
88. T3 作为接口设计、适配实现和交互行为的参考；是否接入其服务，按具体收益决定，不预先绑定。
89. DeepSeek 原型用于参考任务与执行器分离、事件处理和人工介入机制，不整体照搬其单仓库业务模型。
90. 底座验收标准是：上层不必理解各 harness 的协议差异，就能可靠发起、观察、交互、停止和恢复 agent 工作，同时保留必要的原生能力。

## 任务驱动补充（2026-11-02）

91. Coordica 采用任务驱动，而不是用户对话驱动。对话是提交任务和补充信息的入口；任务拥有独立生命周期，会话是执行资源。

本轮 Owner 同时明确 R89 的参考来源为 `deepseek-ai/dsh-superagent-prototype`。
行为解释及参考边界见 [任务驱动方案](TASK_DRIVEN.md)；新增要求不代表授权开始功能实施。

## 任务与待处理边界补充（2026-11-02）

92. 底座保留任务调度、执行事实、原生待处理请求及恢复条件，提供“任务”和“待处理”两类最小运行视图。
    需求池和业务审查池归上层应用；“待处理”取代“阻断池”作为界面名称，从来源事实推导，不另建重复状态机。
    正常排队、依赖等待及可自动恢复的额度等待不默认要求人工；处理操作必须回到具体请求或恢复用例并检查权限与版本。
    上层仍决定业务验收、审查与发布；迁移保留现有开发门禁、历史记录和证据。

Owner 已确认上述方案并要求更新任务表。细节见 [任务与待处理边界](POOL_BOUNDARIES.md)。
此决定授权规划更新，不授权删除现有页面、数据或启动功能实施。

## 聚合底座首版范围纠正（R2026-11-02.4）

93. 唯一目标是多 harness 聚合底座。首版由调用方为每次 Run/Assignment 明确指定 harness/实例，固定机器与工作区；整个 Task 不永久绑定单一 Agent。不自动挑选“最佳”执行器，也不自动降低模型要求。
94. 统一记录 Task、逻辑 Thread、原生 Session、实际执行实例/机器/工作区、产物及进度；每次运行保留所选 provider 和原生绑定，逻辑线程不等于可跨厂商复用的原生上下文。
95. 首版先把指定一家执行与统一记录做扎实，再由第二种 harness 验证共性。跨 harness 显式切换和摘要交接后置，不作为首版完工前提；不宣称原生状态无损迁移。
96. 更早用 Codex 最小垂直接入驱动必要的任务、会话、事件、输入和审批契约；幂等、单写、权限、代际与停止确认仍属必要控制层，不能先建设完整通用状态平台再接原生。
97. 个人助理、公司信息管理、Chief、开发业务工作台等属于未来上层应用；本批不规划或实施其功能。复杂父子编排、竞赛投票、自动选优及按额度自动切换后置。
98. 基本公共接口不依赖完整父子编排或额度策略；底座验收不依赖上层开发应用迁移或完整业务 UI，只保留必要旧流程兼容回归和最小诊断客户端。离线、源码声明与真实 harness 验证继续分开记录。
99. 任务上下文跟随 Task：需求、约束、决策、进度、产物和可见交接记录以任务及版本关联；Thread 是交互入口/记录，原生 Session 和机器是执行资源。不把保存任务上下文描述为迁移隐藏推理或原生内部状态。
100. 吸收 DeepSeek Super-agent 的任务/派工解耦、前台接收路由与后台执行分离、事件触发和持久任务状态；使用既有 Task/Input/Wake/Run 语义，任务有唯一调度负责人，执行者按明确 Assignment 工作和回报。自驱动是授权事件推进，不是每个 Agent 的无限循环，不默认启用自动多 Agent 编排。

与 R2026-11-02.3 的差异是首版范围与依赖顺序，不删除旧需求：R35–R42/R65–R67 的完整策略后置，
R71–R76 保留为边界示例且不列上层开发任务；R77–R78 不要求首版实施迁移。R21–R30/R43–R59 的必要控制与可靠性保留。
本批仍仅 C01–C08 云端离线实现、C09–C12 准备；真实订阅调用、部署和发布授权没有扩大。

## 首期聚合优先（R2026-11-02.5）

101. 首期先做好多 harness 聚合：明确选择原生 harness/实例执行，统一 Task/逻辑 Thread/native Session、机器/工作区、进度和产物记录，以及必要输入、中断、原生审批、恢复和安全幂等。多 Agent 协作、自驱动编排、总管调度、复杂父子任务/自动拆解和跨 harness 接力后置。保留有用架构接口与 DeepSeek 调研；TaskInput/Wake 仅在可靠性确有需要时采用最小原语，不接自主派工，不为后置方向堆未用代码。任务上下文仍归 Task，不强绑 Git 或业务审查。

此项覆盖 R100 和 R2026-11-02.4 方案中把协作/自驱动机制列入首期实现或验收的安排，不删除历史研究。
必要的显式输入排队/投递、审批答复返回当前原生执行、命令幂等和停止确认仍属首期可靠性；它们不等于自主决定下一项工作。
本批仍 C01–C08 离线实现、C09–C12 准备，真实调用、部署、发布和定时任务授权没有变化。
